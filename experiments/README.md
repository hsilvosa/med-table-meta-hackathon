# Experiments (spikes)

Throw-away scripts that de-risked the design. Run from the repository root. They read `data/` (CIMA photos, cut-outs, scenes) and write to `experiments/out/` (ignored by git). SAM scripts need `.venv-sam3`; the rest run with `.venv-app`. The VLM scripts need a local llama-server on port 8082 (command in `vlm_client.py`).

| Script | What it tests |
|---|---|
| `sam3_image_smoke.py` | SAM 3 image model with text prompts on synthetic scenes |
| `sam31_video_smoke.py` | SAM 3.1 multiplex checkpoint on a still image, with the Windows / consumer-GPU workarounds |
| `sam3_box_crops.py` | SAM 3 "box" crops of the scenes, matched to ground truth (IoU >= 0.5) |
| `vlm_read_packs.py` | Qwen3.5-9B reading CIMA pack photos; CN checked against check digit and CIMA |
| `vlm_eval.py` | Qwen3.5-9B on the SAM crops and on a fictional medication sheet |
| `decode_robustness.py` | How small and blurred a rendered pack Data Matrix can be and still decode (zxing-cpp, whole image vs tiled) |
| `meta_smoke.py` | Meta Model API client (`muse-spark-1.3`): connectivity, one pack photo, the fictional sheet, cost per call |
| `sheet_reader_eval.py` | `sheet_reader.read_sheet` (Meta or local backend) scored against the fictional sheet's truth |
| `candidates_eval.py` | For SAM crops without a code: does the model's reading plus CIMA search put the true medicine among the candidates? |
| `blender_decode_eval.py` | Decode rate of Data Matrix codes on Blender-rendered table scenes by camera height (needs Blender 4.5) |
| `eval_photos.py` | Evaluation harness for a folder of photos with a `truth.json` (the packs present, by Codigo Nacional): verified correct, code found but unverified, missed, and the headline number, verified-wrong, with Clopper-Pearson intervals. Ready for the real photos; checked on the Blender scenes (48/48 at 0.5 m, 16/48 at 0.9 m, 0 verified-wrong) |
| `demo_real_plan.py` | Same, with real CIMA data from the local cache (Sintrom, paracetamol, Gelocatil, enalapril): shows real quotes on paper |
| `eval_world.py` | Pipeline on photos taken in the 3D room (`web/`, `scripts/serve_world.py`): codes read against the room's own ground truth, confident-wrong count, rates by camera height and by pixels per module |
| `world_candidates_eval.py` | Boxes without a visible code in room photos: SAM 3 finds the box, the model proposes CIMA candidates |
| `demo_plan.py` | Builds a demo plan from invented medicines: PDF, `.ics`, voice WAVs, PNG preview |
| `make_fictional_sheet.py` | Renders the fictional medication sheet with phone-photo degradations |

## Results (2026-10-26; small samples, read them as indications, not metrics)

- **SAM 3 / 3.1 run on an RTX 3060 under Windows** (5.4 GB / 6.4 GB peak, 1-2 s per prompt). They need bf16 autocast; SAM 3.1 also needs `use_fa3=False` and a wrapper around an upstream `init_state` argument bug (see the script). On 12 synthetic scenes SAM 3 matched 71 of 72 ground-truth packs (IoU >= 0.5) and made 10 extra detections.
- **Cut-outs (`scripts/make_cutouts.py`)**: on 50 random medicines, 50 pack cut-outs and 51 dosage-form cut-outs passed the checks; by eye the packs are whole and the pills clean. 3 of 31 oral-solid medicines got no pill.
- **Qwen3.5-9B on full CIMA pack photos**: brand or ingredient matched in 7 of 8; 6 CN reads, 5 accepted (check digit valid and present in CIMA for that medicine), 1 rejected by the check digit.
- **Qwen3.5-9B on small crops from synthetic scenes (73 crops, about 300 px, rotated, partly occluded)**: by the crude name check 28 correct, 2 abstentions, 43 wrong; 15 CN reads, 8 with a valid check digit, 6 of those present in CIMA for the true medicine. Wrong answers include invented ingredients and look-alike confusions. The check is crude (it also counts as wrong correct ingredients given without the brand, e.g. Xelevia read as MSD/sitagliptin), but the conclusion holds: the model must not identify packs. Identification comes from the pack code; the model only proposes candidates that the user confirms, and a CN is accepted only if the check digit, CIMA membership and the other fields agree.
- **Qwen3.5-9B on the fictional medication sheet**: 7/7 rows, 28/28 schedule cells and all remarks exact, 15 s. One clean synthetic sheet; real sheets are untested, so every line still needs caregiver confirmation.
- **Data Matrix robustness (`decode_robustness.py`, rendered square Data Matrix, 6 trials per cell, so only a rough guide)**: decoding works from about 3 pixels per module with blur up to 1 px, and needs about 5 pixels per module with blur of 2 px; at 2 pixels per module it fails once there is any blur. The tiled search adds little over decoding the whole image (4 px/module with blur 2: 0/6 vs 3/6) and costs about 0.4 s instead of 0.03 s. A pack code is about 1 cm for 22-26 modules, so a 12 MP photo (4000 px) of a table 60 cm wide gives only about 2.7 pixels per module: borderline.
- **Blender scenes (`blender_decode_eval.py`, `scripts/blender_scene.py`, 8 scenes per height, 5-7 boxes each, 4000x3000 phone-like camera of about 71 degrees, 12 mm square code on the top face, random pose, tilt up to 20 degrees, one area light; only codes inside the frame counted)**: codes read exactly (with the tiled search) at a camera height of 0.25 m: 19/19, 0.35 m: 41/41 (5.8 px/module), 0.5 m: 48/48 (3.9 px/module), 0.7 m: 45/48, 94 % (2.8 px/module), 0.9 m: 16/48, 33 % (2.0 px/module). With very glossy surfaces (roughness 0.05): 0.35 m 98 %, 0.5 m 98 %, 0.7 m 88 %. Practical rule for the app: photograph from 50 cm or closer. These are perfect labels on flat boxes with no print defects, curvature or motion blur, so they are an upper bound for real packs; real photos are still unmeasured.
- **Two test-tool findings**: (1) zxing-cpp in GS1 mode writes long rectangular symbols (for example 8x64 modules) that real packs do not use and cannot be forced square, so the test generator now writes square ECC200 symbols with libdmtx (22x22 to 26x26 modules) carrying the same text; the earlier numbers with rectangular symbols were very similar. (2) `pylibdmtx` did not import on Python 3.12 (needs `distutils`), so the libdmtx fallback in `decode.py` had silently been disabled; `setuptools<81` fixes it and a test now fails if it breaks again.

- **Meta Model API (`muse-spark-1.3`, standard tier)**: the token works from Spain. Three calls cost USD 0.0096 in total: about USD 0.005 per image call (3,081 input tokens for a 1024x576 pack photo, 173 output of which 115 hidden reasoning; the sheet: 1,724 in, 638 out). `reasoning_effort` accepts minimal/low/medium/high/xhigh/max (not "none" for this model). On the one pack photo tried, the brand, ingredient, strength and form were right, but the Codigo Nacional was misread (648228.9 against CIMA's 848226); the check digit rejected it, which is the intended safeguard. On the sheet, the first five rows printed matched the truth exactly (the printout was cut at 700 characters); a full scored comparison against Qwen has not been run.
- **Sheet reader with Muse Spark (`muse-spark-1.3`, `sheet_reader_eval.py`, 2026-10-26)**: on the same fictional sheet, 7/7 rows, 28/28 schedule cells and all remarks exact, USD 0.0051, one call. Same caveat as for Qwen: one clean synthetic sheet, so real sheets are untested and every row still needs caregiver confirmation. Doses that do not parse (e.g. "media") are kept as read and block the line instead of being turned into 0.
- **Candidates for packs without a readable code (`candidates_eval.py`, Muse Spark, 12 crops of about 300 px from synthetic scenes, so an indication only)**: the true medicine was the first candidate in 3 of 12 and within the first four in 3 of 12; in 6 the model read nothing and gave no candidates (an acceptable outcome: the caregiver is asked), and in 3 it read a different brand. One wrong read (BETOPTIC for a Casenlax crop) even passed the check digit and exists in CIMA, a valid code for the wrong medicine, probably text of an overlapping pack. This is why the model's reading is only a search query: candidates are shown with the official photo and never enter the plan without the caregiver's confirmation. Through the app with scene_0000 (SAM 3 as a subprocess, about 24 s): 7 boxes without code, 3 proposals, one candidate confirmed and added as `confirmed`.
- **3D room (`scripts/build_world.py`, `web/`, `experiments/eval_world.py`, 70 photos of 4000x3000 from random viewpoints, 0.3 to 0.9 m above the table, tilt up to 25 degrees, random yaw, mild phone effects: 0.9 px blur, noise, JPEG q88; second version of the room, with the medicines of an older patient on many drugs placed first)**: 194 codes in view. 122 verified correctly (62.9 %, 95 % CI 55.7-69.7), the 11 deliberately unknown CNs stayed unverified as intended, 61 not read. Confident-wrong: 0 of 122 verified (95 % upper bound 3.0 %). Expiry flag wrong: 0. By camera height above the table: under 0.4 m 19/20, 0.4-0.5 m 10/10, 0.5-0.6 m 37/37 (95-100 %), 0.6-0.75 m 62/74 (84 %), over 0.75 m 5/53 (9 %). By pixels per module: under 2: 1/32; 2-3: 90/119 (76 %); 3-4: 26/26; 4-6: 15/16. Same story as the Blender scenes and as the first version of the room (0 of 140 confident-wrong, 96-100 % up to 60 cm): photograph from 60 cm or closer. The room is a stage set (flat cut-outs with stickers generated here), so this is an upper bound that says nothing about printed codes on real packs.
- **A real printed code was read by accident (room build)**: the official CIMA studio photo of one pack (Omeprazol Cinfa 20 mg) shows a real printed Data Matrix. The pipeline read it, verified it in CIMA and flagged it as expired (its example date is in the past), and next to our sticker the same box counted as two medicines. `build_world.py` now paints printed codes over before adding the sticker and asserts that none survives. Side effect worth knowing: a box that carries two different codes is reported as two packs (see the open items in `PLAN.md`).
- **Bookkeeping bugs found while building the room's ground truth (all in the test bench, none in the pipeline)**: a ray aimed at the exact centre of a quad can slip between its two triangles, so a visible sticker was counted as hidden and showed up as a false 'verified wrong'; and a cut-out is a rectangle with transparent corners, so rays must ignore transparent pixels or a box 'hides' its neighbour's label. After the fixes the confident-wrong count went from 2 to 0 on the same poses. Also: browsers pause `requestAnimationFrame` in hidden tabs, so the photo function reads the player's pose directly instead of the render loop's camera.
- **Boxes without a visible code in the room (`world_candidates_eval.py`, Muse Spark, 2 photos within 0.6 m, so n = 2 boxes and only an anecdote)**: SAM 3 found both boxes; the model read the brand correctly (Rivastigmina Sandoz) but the true medicine was in the first four candidates, not first, because the same brand exists in several strengths. The caregiver picks. In the second version of the room, through the app with one box (Atorvastatina Cinfa 20 mg, no sticker): SAM 3 found it and Muse Spark proposed the right medicine first (again n = 1, an anecdote); the app labels it as a model reading to check against the box.
- **Sheet reader on the 10-row fictional sheet of the room (`sheet_reader_eval.py`, Muse Spark, 2026-10-27)**: 10/10 rows, 40/40 schedule cells and all remarks exact, USD 0.0054, one call. The sheet lists eight of the boxes of the room plus bisoprolol (on the sheet, on no table), while amlodipine is on a table and not on the sheet. Same caveat as before: one clean synthetic sheet.
- **Bugs found only by driving the real app in a browser (all fixed, each with a regression test)**: (1) a schedule read from a photo filled the data but the dose buttons still showed "None", because Streamlit keeps a widget's old value in the browser under an unchanged key (the row's widget keys now carry a revision); (2) going forward and back a screen emptied the file uploader, and the code took that for "the user removed the photos", losing the photos and boxes on the next action (it now removes only what the user removed, and lists the photos used so far with a Remove button); (3) the PDF lacked the patient name and notes because the only place to type them was an easily missed optional field on the last screen.
- **Reading at 90 cm (`decode.find_zoomed`, `experiments/lowres_probe.py`, `zoom_diag.py`, `eval_world.py`; 2026-10-27)**: the first version of the pipeline read 9 % of the codes seen from more than 75 cm (about 1.6 pixels per module with a 12 MP phone at 90 cm, too coarse to sample). The information is still in the pixels: with the position of each code taken from the room's truth, an enlarged and sharpened crop decoded 39 of 40 of them. The fix is a dense scan of overlapping 640 px windows, each enlarged 2x (gentle sharpening) and 3x/4x (heavy unsharp mask, and an adaptive threshold of the sharpened image), read with zxing-cpp; GS1 parsing, the CN check digit and the CIMA lookup are unchanged, so a misread cannot become a verified pack. Results on photos NOT used to design it (random viewpoints 85-95 cm above the table, tilt up to 20 degrees, phone effects on): 12 MP, 40 photos, 158 codes in view: 137 verified correctly, 13 deliberately unknown CNs unverified as intended, 8 not read (94.5 % of the codes that can be read; the misses sit at 1.4-1.8 px/module); confident-wrong 0 of 137 (95 % upper bound 2.7 %). 48 MP (same lens, four times the pixels, blur scaled with the pixel size), 30 photos, 116 codes: 106 verified, 8 unknown as intended, 2 not read (98.1 %); confident-wrong 0 of 106 (upper bound 3.4 %). Time per photo: about 3 s at 12 MP, 7 s at 48 MP. Two photos of the same view taken a few millimetres apart (hand shake) add little: 93 % alone, 94 % for the union of the pair, because the misses are the same codes; a retake from closer is what helps.
- **Honest limits of that result**: (1) the room is a stage set with flat stickers, so this is an upper bound for printed codes on curved, glossy or creased cartons; (2) the sticker is 12 mm wide, the usual size of a pharmaceutical Data Matrix, but I have not measured real packs; (3) the 48 MP numbers assume a phone whose main camera really shoots 48 MP (many current flagships do, usually as an optional mode); (4) the fix has a floor: synthetic codes with 0.9 px of blur are read from 1.8 px/module and not at 1.6 and below (`tests/test_decode_lowres.py`).
- **Where it stops (same scan, fresh photos)**: 12 MP at 1.0-1.1 m: 47 of 106 codes read (about 1.5 px/module); 48 MP at 1.15-1.25 m: 19 of 108 verified (2.6-2.8 px/module, which would be plenty if the image were sharp). The limit beyond about 1 m is not the pixel count but the blur of the lens: the simulated phone blurs by a fixed angle (0.9 px at 12 MP), so the blur grows relative to a module as the camera moves away (0.56 of a module at 90 cm, 0.62 at 1 m, 0.67 at 1.2 m with 48 MP) and the modules smear into each other. A real lens may be sharper or worse than the 0.9 px assumed here; this is an assumption of the simulation, not a measurement of any phone. Practical limit of the tool: 90 cm works, 1 m is unreliable, more does not.
- **Room batch of 72 photos from 0.3 to 0.9 m (re-run with the zoomed scan; part of the same photos the scan was first checked on, so not independent)**: 187 of 204 codes verified, 14 unknown CNs unverified as intended, 3 not read (98.4 % of the readable ones); by height above the table: under 0.75 m 142 of 145 read, over 0.75 m 59 of 59; confident-wrong 0 of 187 (upper bound 2.0 %).
- **Live scan feasibility (`experiments/live_scan_probe.py`; 2026-10-27)**: how many of the codes in view a preview frame reads if it is smaller or scanned with fewer passes (30 room photos, 95 codes; part of them were used to tune the scan, so this shows the trend, it is not an independent figure). Frame width 1333 px: 0-6 % beyond 0.5 m. 2000 px: 62 % at 0.5-0.75 m and 0 % at 0.75-1.0 m. Full 4000 px with the two fast passes (`decode.LIVE_PASSES`): 97 % at 0.5-0.75 m, 93 % at 0.75-1.0 m, 1.3 s per frame, against 98 % and 4.2 s with the four passes of the photo. So the room's live scan sends a full 12 MP frame and uses the fast passes. In the room a scan takes about 2 s from still frame to the last box, including the frame capture, the upload and the phone effects; the server answers in stages (plain read, then each fast pass), so boxes appear one by one: on 8 fresh 90 cm photos the plain read found 0 of 29 codes in view (0.1 s), the first pass 15 (0.4 s) and the second 22 (1.3 s). It scans only when the phone has been still for 0.3 s, never twice for the same view, and waits at least 1.5 times as long as the last scan took before the next one.
- **Light box finder and "no code read" boxes (`src/medtable/boxes.py`, `experiments/eval_boxes.py`; 2026-10-27)**: when no code is read from a pack, the live preview draws an amber dashed box on it ("No code read: move closer or add it by hand") and the planner shows a card asking for a close-up. The finder is classical image processing, not a model: the most common colour of the photo is the table, a pack is a compact region of a pack-like size whose colour differs from it, and a region with almost no dark marks (plain paper, a shadow, a seam between boards) is dropped because every pack has printed text. It identifies nothing; it only says "a pack-sized thing is here". The room now writes where every pack is into each photo's truth file, so the finder is measured against the real positions. Wood table (the room's), 12 MP, 0.5-0.95 m above the table, tilt up to 20 degrees, phone effects on, "clear" packs = entirely in frame and at least 75 % visible:
  - Batch used to design it (60 photos, 99 clear packs): 97 found as a region (98.0 %); of 16 packs with no code read, 15 flagged amber; 0 of 17 amber boxes on something that is not a pack. The thresholds were set on this batch.
  - New batch with another seed (60 photos, 112 clear packs), measured before the last rule change: 110 found (98.2 %); of 20 packs with no code read (18 without a sticker, 2 with a sticker the fast scan did not read) 19 flagged amber (95 %); 1 of 22 amber boxes was on something that is not a pack (a dark shadow on the neighbouring table). That failure made me widen the "no printing" rule from "paper" to any region with no dark marks; with it the 1 false box disappears and no pack is lost, but this batch is no longer independent of the design.
  - Close-ups (40 photos at 0.3-0.45 m, 18 clear packs): 18 found, the 1 pack with no code flagged, 0 false boxes. A close-up of this kind reads 19 of 20 codes below 0.4 m (the room evaluation above), against about 93 % at 90 cm. In the room, pressing "Close-up of the box with no code" put the phone 35 cm above a pack whose sticker had not been read from 95 cm, and the code was read (green box). A pack that has no code at all (atorvastatin in the room) stays amber, now with "No code read: add it by hand".
  - **Limits**: on a white table it finds 13 % of the packs (30 photos, 67 clear packs) and 4 of its 6 amber boxes are not packs; on a dark table 71 % (55 clear packs; 7 of 12 packs with no code flagged). When it fails it mostly stays silent, but a missing amber box means nothing: it does not say that every pack has a code. Two packs that touch are one region. A pack with almost no printed text is taken for paper. It has never been run on a real photo of a cluttered table. The sheet of paper in the room is correctly ignored, but only 11 regions of it were seen.
